# The tick boundary (`/start-multi`)

Why `/start-multi` ends its context at a wave boundary rather than running a fleet to
completion, and the five preconditions that make that safe. Extracted from
[`commands/start-multi.md`](../commands/start-multi.md) under ADR-012's ceiling, and
**normative**: the command's "The tick boundary" section points here and adds nothing.


**You are a tick, not a session.** When every unit of the wave you dispatched is terminal (`passed`, `failed`, `blocked`) or in the current escalation batch, stop dispatching, finish steps 5-8 for this wave, and **end your context**. A later wave belongs to the **next** tick, on a fresh context against the same `run.yaml`: resume is unchanged — `run.yaml` present and no `--fresh` — and per-tick cost is bounded by one wave, not by the fleet. Ending is safe only because of the five preconditions below, each of which fails **silently** if dropped, so none is optional.

1. **`git push` every started lane's branch and keep every worktree this tick touched.** A lane short of `/verify-build` has pushed nothing, so an unpushed wave is commits in one directory on one machine: the next tick resumes from a branch that never saw them, and a recycled worktree loses them. This is why step 7 removes a worktree only for a unit already `terminal: true`: your push satisfies "branch is pushed" for every lane in the wave, so a lane left non-terminal — gate-red, escalated, resumable — keeps its worktree even though its branch is now pushed, and its teardown belongs to whichever later tick finds it terminal. **Your own commits count too**: push `int/<run-id>` and any orchestrator-authored base commit, or a later tick reads a stale `origin/int` and misses the wave you merged — unless step 5's gate is red, and a red base is never pushed.
2. **Hold no lock directory and leave no background `heartbeat` refresher alive.** Release every lock you took — `rm -rf` the whole directory, as step 2 requires — and stop your refresher before printing anything. It dies with this context, so a lock left held is reclaimable only after the full `now − mtime > 5 × interval` wait on two reads, paid by every later tick before any lane runs, and reads as slowness, not a leak.
3. **Stamp every `agents.yaml` row you wrote with `tick: <n>`**, where `n` is `1 +` the highest `tick` already in `agents.yaml` (no rows, or rows predating the stamp, means tick 1). The file has two readers with two lifetimes. Addressing resolves a `SendMessage` recipient **only** from rows stamped with the current tick, because an `agentId` dies with the session that spawned it and a message to a dead agent is indistinguishable from a lane not answering; attribution (`/run-report --fleet`) reads **every** tick's rows, because N sessions are still one run. An unstamped row is addressable by no tick.
4. **Derive where the run got to; store only what no unit determines.** Wave progress is `units[].wave` plus `step`/`status`, cross-checked against `git log origin/<default>..<each unit's branch>` as step 4 requires — git is the primary signal, the state file a hint. `run.yaml` gains exactly two keys for the yield, `waveBudget` and `spendToDate`: the first a policy input no unit can compute, the second an accumulator nothing can project from `units[]`, written as an addend at each boundary because after the yield no context is long enough to notice its growth. A `wavesDone:` or `phase:` key is a second, staler answer to what the units already answer — "a state file that says `step: plan` while the branch carries three slices" is the orchestrator's commonest misread, per [`unit-lane`](../agents/unit-lane.md).
5. **Print the verdict as your last act**, at column 0 with nothing after it, and take no turn after it:

        FLEET-STEP:v1 outcome=success waves=<k>/<N> units=<t>/<u>

    `k` is the waves now complete, `N` the wave count step 1's sort produced; `t` the units at a terminal status, `u` every unit in `run.yaml`. The outcome vocabulary is `success`, `gate-red`, `blocked-on` — there is no fourth word: a wave short of the total is a `success` whose `waves=` is short, as `/build` spells its own yield one level down. `gate-red` is a red gate you own (step 5's base gate), `blocked-on=<what>` a tick that could not proceed at all, `waves=<N>/<N>` a run that finished — the driver stops on that and on a `k` that did not advance. An absent line is `infra`, and `infra` is retried.

    **The verdict is blocking**: never end your turn waiting on a background task or a notification — your turn ending *is* the tick ending, so nothing arrives and a finished wave loses its verdict. Await any gate the verdict depends on inside the tick.

`--serial` (`reference/start-multi-serial.md`) is untouched here: whether a serialised run yields on this boundary **is decided there, and the answer is never**.
