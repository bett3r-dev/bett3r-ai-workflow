# /start-multi — parallel delivery across worktrees

Drive a **list of work units** through the standard flow in parallel, isolating each in its own git worktree. You (the main session) are the **orchestrator**: you dispatch, verify git state with your own commands, collect escalations, and resume. You do **not** implement.

Run state lives in `.work/multi/<run-id>/run.yaml` — ephemeral, gitignored, and the **resumable** source of truth. Re-running the same set resumes it.

## Argument: $ARGUMENTS
Work-unit ids (+ optional descriptions), then flags.

| Flag | Effect |
|---|---|
| `--deps "C:P,..."` | Dependencies (child stacks on parent). The only dep source besides asking once. |
| `--dry-run` | Print the wave / worktree / branch-base plan; cut nothing. |
| `--max-parallel N` | Cap concurrent unit agents (default conservative — see Principles). |
| `--no-pr` | Stop after local per-slice commits; don't push / open PRs. |
| `--gate-design` | Pause after `design` on **every** unit (default: only design-heavy ones). |
| `--serial` | No cross-unit parallelism; run each unit's pipeline yourself, dispatching the real `executor`/`verifier`/`test-runner` agents. The rigor path. |
| `--keep-worktrees` · `--fresh` · `--run-id <id>` | Teardown / resume-state controls. |

## Per-unit pipeline
`start → design → plan → build → verify-build` (the standard flow, unattended). Each unit ends at a pushed **ready-for-review** PR whose body is the record. When a unit's ticket carries a `design-multi:resolved:vN` block (see step 0), its `design` step still runs — but the answers are already in the ticket, so it acts as a **verification second pass** that escalates only on code drift (step 4).

## Steps

**0 — Acquire & snapshot (the only tracker touch).** Resolve `run-id` (default `multi-` + sorted ids). If `run.yaml` exists and not `--fresh` → **resume** (skip to step 4). Else fetch each unit's content from the tracker **once**, snapshot it into the run dir (agents read the snapshot, never the tracker again). Pin the base: `git fetch origin`; `BASE=$(git rev-parse origin/<default-branch>)`. Mark design-heavy units (description markers, or `--gate-design`). **Detect a `design-multi:resolved:vN` block in the snapshot — grep the token, which is emitted both as an HTML comment and as a visible inline-code line, because some trackers strip comment nodes. If present, mark the unit `designResolved` with its `resolvedBase` — such a unit is *not* design-heavy (its human interview already happened in `/design-multi`).** This reader knows `:v1` and `:v2`; a `:vN` it does not know is unparseable — escalate rather than guess at a newer shape. **From `:v2` the block carries `status=ready | deferred | blocked | umbrella`: skip anything not `ready` and log why** (a `:v1` block has no field and is read as `ready`). Multi-ticket design runs routinely yield deferrals, units blocked on human-supplied secrets, and umbrella parents with no net-new code; picking one up unattended burns a lane and can open a bad PR. Write `run.yaml`, all units `pending`.

  **Snapshot without re-reading.** A resolved block runs ~10k tokens; reading it into context and re-emitting it verbatim pays for it twice before any agent starts. Write from the raw response (a scripted fetch straight to `units/<id>.ticket.md`). You need the marker, its `base=` sha, the summary and the repos touched — reading the block is the unit agent's job.

  Then derive, per unit, four things **no lane can compute for itself**:

  - **Drift, per unit — never per run.** `git diff --stat <resolvedBase>..<BASE> -- <unit's named files>` → `none | lines | structural`. One run-level note cannot say *"zero drift on two surfaces, +1248/−732 across 31 files on the third"*.
  - **A runner + glob map**: `surface → runner → include/exclude globs → can it see this unit's paths, y/n`. Resolve to the **glob** — "vitest runs this package" is worthless when `include` is `*.test.ts` and the suites are `.test.tsx`. A unit no runner collects must say so rather than let a green count imply coverage.
  - **The repo each unit belongs to** (kinds below) and its own base — a cross-repo unit's base is not `BASE`.
  - **The host repo's build/test preconditions** — `CLAUDE.md` and **every** `.claude/rules/` file, *ignoring* `paths:` frontmatter. Path-gating is a context-loading optimisation: at worktree-prep no test file is in context, so the one rule you need structurally cannot fire.

  **Re-resolve every PR the resolved designs cite** (`gh pr view <n> --json state`) — such a claim is stale by dispatch, and a `MERGED` stack parent is a **base correction**, not an escalation. Phrase handed-down tracker facts as *"verify at BASE whether X"*, never as assertions; your recall is the least reliable input in the run.

  **Three unit kinds**, because "unit == a host-repo worktree" is not always true. **Standard**: host-repo work with a build loop. **Multi-repo**: checkouts of 2+ repos, one primary (where the branch and PR live). **Cross-repo / no-build**: zero host-repo changes, so no worktree allocated, `worktreeCreated: false`, and the pipeline collapses to the landing tail (gate → push → PR). Record `repo:` and `runner: agent | orchestrator`. The deciding test: **if the target repo is outside the session's working directories, an unattended agent cannot complete outward-facing steps there — you run it.** Mixed-repo fleets are the normal shape of "land the deferred work from PR #X"; unnamed, the vocabulary pushes toward a pointless branch and an agent whose first write blocks forever.

**1 — Deps → waves.** Populate deps from `--deps`, or ask **once** if >1 unit — but **read the resolved blocks before you re-interview.** A resolved block is an interview transcript, and it routinely settles file overlap in writing ("no shared files, safe in parallel"). Where every unit is `designResolved` and the blocks speak to overlap, derive `deps` and write a `depsRationale` quoting them; ask only about the units the blocks do not cover. Every question the blocks already answered is a place this handoff leaks back into human time. Treat the derivation as a **hypothesis about diffs that did not exist when it was written** — step 8 verifies it. Topologically sort into waves; detect cycles → stop. Never read tracker links (their direction/coupling is unreliable).

**2 — Worktrees & branches: `install` is not `ready`.** A worktree is ready when the artifacts its own tests import exist on disk — not when the checkout is cut. Per unit (wave order): pick a **clean** worktree (reuse an unassigned one, else `git worktree add --detach`); one unit per worktree; **never a dirty worktree**. Branch base: independent → `BASE`; stacked → the parent's committed tip. Cut the branch, then **verify the base yourself** — independent: `git -C <wt> rev-list --count HEAD..origin/<default>` must be `0`; stacked: `git -C <wt> merge-base --is-ancestor <parent-tip> HEAD`. `--dry-run` prints the resolved plan and stops here. Then provision, all of it before any agent is dispatched:

  - **Install *and* build**, preferring the recursive script (`build:all`, `turbo build`) over a bare `build` — a `tsc --build` monorepo may emit only the module format `exports.import` does *not* point at. Workspace deps resolve through a gitignored `build/`, absent in every fresh worktree, so this hits **every unit of every run**, presenting as "40 of 57 files collected zero tests" or `Failed to resolve entry for package` — which reads as a broken baseline rather than a missing step. Fixed once here, or paid N times in parallel by agents who each get it wrong independently.
  - **Archive (never delete) a reused worktree's `.work/`.** The dangerous files are exactly the ones the flow reads back — `design.md`, `slices.yaml`, `pr-body.md`, `decisions.md` — and a populated `slices.yaml` gives a lane every reason to build a different ticket. Stale and current are distinguishable **only by mtime**, and `.work/` is gitignored so `git status` is clean. Archive into the run dir: those buffers include the `learnings.md` step 6 exists to rescue. Also **re-emit composite `build/*.d.ts`** — a switched branch leaves phantom `TS6305` cascades the transpile-only build never surfaces. Cheap belt-and-braces: **stamp the ticket id into the first line of every scaffolded `.work/` file**, so a missed scrub shows on the first read rather than on inspection.
  - **Lay a multi-repo unit out by *repo*, not by ticket** — `<RUN>/wt/<unit>/<repo>` — so the relative path between checkouts matches the one between their canonical clones. Otherwise every `portal:` / `file:` / `link:` / relative `workspace:` specifier between them breaks, and it is a hard block: `yarn install` dies with `Manifest not found`, which points at a manifest rather than at the layout. Verify such specifiers resolve at cut time.
  - **Give each unit its own scratchpad subdirectory** (`<scratchpad>/<unit-id>/`) and pass *that* in the brief. Worktrees are isolated; the session scratchpad is not — one lane's `pr-body.md` has silently clobbered another's, and the exposure grows as the brief standardises filenames.
  - **Write `.work/known-baseline-failures.md`** per unit, exactly as `/start` step 4 specifies (freshly-built tree, capture method recorded, incremental state cleared). Here you pay once instead of N times in parallel — and a wrong *shared* baseline is worse than none, because lanes either chase errors that are not theirs or treat real new ones as pre-existing cover.

  **Size `--max-parallel` by memory, not cores.** Past some N the fleet falls off a **cliff**, not a slope — one build measured 95 s alone and >38 min under load at swap 31.9 GB of 33.8. Scope the per-unit gate to touched packages (a server-side unit rarely needs the web bundles) and serialize `generate-all`-class steps behind a lock. Contention is also the mechanism behind the 600 s deadlock, and a starved lane reads as a hung one — log load average / swap when a gate overruns.

**3 — Dispatch.** Process **waves in order**; within a wave launch background agents up to `--max-parallel` (queue the rest). A stacked child waits for its parent's **commit**. Each agent is worktree-scoped, runs the per-unit pipeline against its worktree, and writes **only** its own `<run>/units/<id>.state.yaml`. **Single-writer rule:** only you write `run.yaml` (aggregate the per-unit files) — this prevents concurrent-write races. **Failure isolation:** a unit that fails unrecoverably is marked `failed`, the others continue, and any unit stacked on it becomes `blocked`. **Learnings, not issues:** an agent that hits friction in the *flow itself* (a gate that misfired, a skill that misled, a step that fought the grain) `record`s it to its worktree's `.work/learnings.md` — **buffer only**. Never `/capture-learnings` inside an unattended agent: it files GitHub issues one-confirm-each and dedups against the backlog, so N agents racing it produce duplicate / wrong-repo issues. The orchestrator rescues the buffers before teardown (step 6) and captures once at the end (step 8). (`--serial`: run each unit yourself with the real executor/verifier/test-runner agents — full rigor, no cross-unit parallelism.)

  **Address every message; never resolve a recipient from recall.** Write `<run>/agents.yaml` (`unitId`, `agentId`, `worktree`, `dispatchedAt`) as each agent launches, resolve from it before every `SendMessage`, and **lead with `TO: <TICKET-ID>`**. You reason in ticket ids and the harness addresses opaque ones; reconstructing that map from dispatch order has misrouted two corrections in one run, silently in both directions — the wrong lane got noise, and the right one never received a directive without which its own AC could not hold. Fleet contract: **a directive whose ticket id is not yours is not acted on — record the misroute and report it.**

  **A directive carries the constraint, never the expression.** Your directives inherit your authority, so implementation-shaped detail is treated as settled and routes around the judgment the dual gate exists to apply. One prescribed `saleTime: data.date ?? existing.saleTime` was implemented faithfully and double-billed a metering period; *"`saleTime` is the bucketing key and must not move when an edit arrives — `date` is mutable"* would have been satisfied **and tested**. The symmetric half, currently missing by omission: **a directive is an input to the lane's judgement, not a settled decision — if it contradicts the code, the code wins and the lane says so.** Where a lane's gate catches one of yours, the PR records the provenance rather than absorbing it.

  **Allocate anything monotonically numbered — ADR numbers above all.** Hand each lane its number in the **initial** brief (by the time a lane wants one it is already writing) and require a **claimed / released** report back, or reserved-but-unused numbers leave permanent holes. Derive from every ref *and* every sibling branch (`git ls-tree <branch> -- <adr-dir>` sees sibling worktrees' unpushed ADRs), never from a remembered number — a contract seeded from a stale one collided on its first slot. Three lanes once picked the same `ADR-057`: different filenames, no conflict, clean merge. Numbering rules live in `domain-modeling/ADR-FORMAT.md`; `/verify-build` re-checks against the merge target regardless. Prefer **amending an existing ADR** where one covers the ground.

  **Nested-agent mechanics invert one level down.** Unit agents dispatch children **synchronously via `Agent`, `run_in_background: false`** — only `Agent` honours it. `SendMessage` cannot be made synchronous, so a lane that resumes a child that way is **idle, not working**, until you resume it; a fix pass must be a fresh `Agent` dispatch, accepting the lost context. Counter-intuitive and worth stating: **the same call is safe for you and unsafe for a lane**, because your backgrounded resumes notify the top-level session normally. Treat every **grandchild** completion as *"resume the owning parent"*, resolved via `agents.yaml`.

**4 — Collect & resume. Git is the primary resume signal; the state file is a hint.** A lane honours "update your state after each pipeline step" literally, and `/build` *is* one step containing N slices — so a unit has read `step: plan, commits: []` while its branch carried two committed slices and a third verified. **Cross-check `git log origin/<default>..HEAD` against the flags** whenever you verify build-complete, and always before cutting a stacked child — the moment a parent's bookkeeping stops being its own business.

  **A stall detector needs a terminal state and a positive control.** Exclude units at `passed`/`failed`: without that, a finished lane and a dead one give identical signals — no writes, no transcript, no commits — so the watchdog cries wolf exactly when the run is going well and gets muted right before it would have been useful. Validate it against a directory you just wrote to before trusting a negative; a detector never seen to fire is not evidence of calm. (`find -newermt '<relative>'` matches **nothing** on BSD/macOS, silently — use `-mmin -N`.) The two stop shapes look identical in the notification and need opposite responses: **completed + ~0 tool uses + untouched branch** is starvation (re-dispatch); **completed + real work + a "standing by" message** is a deadlock (corrective resume).

  **A grandchild's report is not addressed to you.** A `verifier`/`executor`/`test-runner` notification from inside a unit's `/build` loop reaches your session; its "the orchestrator may commit" means the **unit agent**, which already has the result directly. Read it as progress — do not act on it, relay it, or write into that worktree. Volume scales with **slices × units**, the two axes that already multiply, so at any real fan-out these bury the signals that are genuinely yours: a unit escalating, and a unit finishing.

  Aggregate per-unit state into `run.yaml`. Resume any `in_progress` (dead agent) or escalated unit from its next incomplete step — the flow is idempotent: slices already `passes: true` and committed are skipped. **Batch escalations** and present them together as a numbered list — recommendation first, one line of *why* each escalated. Do **not** use `AskUserQuestion`; the user answers free-form. A **design-heavy** unit stops after `design` — surface its `.work/design.md` for review before it proceeds to `plan`. A **design-resolved** unit is not gated: it runs `/design` as normal, but the resolved decisions are already in the ticket, so the grill **verifies rather than re-derives** (see `/design`) and flows straight to `plan`. It escalates only where code drift re-opens a fork the block does not answer — batched like any other. That is the whole mechanism; there is no separate unattended mode to maintain.

**5 — Commit & PR.** Per passed unit, ensure the per-slice commits are in place; then (unless `--no-pr`) run `verify-build` to open the PR **ready for review** — `--base <parent-branch>` if stacked, else the default branch. Record `prUrl`. A stacked child wave may begin once its parent is committed.

  **Re-check the pin before `verify-build`, every time.** `git fetch origin` and compare `origin/<default>` against `createdBaseSha`. Nothing else re-checks it, so the last unit to finish silently eats whatever landed mid-run — and the cost arrives at the worst moment, with the work done, gates green and the PR declared ready. If it moved, name the overlapping files per unit (`git merge-tree`, one command) and record the drift in `run.yaml` so a resumed run inherits it. An external merge is normal collaboration; the defect is only that nobody looked.

  **You own a diamond base.** A two-parent merge is yours, not the child's — a base that does not compile is a foundation whose failures surface deep inside the child. Generated/codegen files → `git checkout --theirs` then re-run the generator, never hand-merge. Hand-authored additive files → splice **complete** units, never a marker-strip: it breaks on array tails and interleaves two partial blocks at their shared prefix. Then build and drift-check the base **green**, and check for `*.orig` residue before committing — a `.ts.orig` is not compiled, so it passes every gate invisibly.

  **A child cut early is stranded on a base its parent then fixes.** Cutting at build-complete is the right throughput call, but every defect `verify-build` exists to find lands *after* the cut. Record `parentTipAtCut`; the child **forward-merges the parent after that `verify-build`**, and again immediately before opening its PR (a PR base is a moving ref, so a stale local base also makes the child's diff misleading). Better: diff `parentTipAtCut..parentHEAD` yourself and **tell the child what changed and why it matters to its work** — it cannot be expected to notice that a commit it never touched invalidates an assumption inside its own slice, and the gap does not surface as a failure: one child's deterministic test would have gone green over the live race its parent had just closed.

**6 — Rescue learnings (before teardown).** Aggregate each unit's worktree buffer `.work/learnings.md` into the run dir (`<run>/learnings.md`), tagged by unit; fold in any flow-friction you hit while dispatching / resuming. This **must precede teardown** — the buffers live in the worktrees and step 7 deletes them. (This subsumes `verify-build`'s per-unit "run `/capture-learnings`" nudge, which an unattended agent can't action; the fleet defers it here.)

**7 — Teardown.** Remove only worktrees **this run created** whose branch is pushed (or whose unit is terminally `failed` and acknowledged). **Never** remove a pre-existing or dirty worktree. Skip if `--keep-worktrees`.

**8 — Report & capture.** Per unit → branch (+ base/stack) → step reached → **PR URL *and* its `mergeable` state** (a unit is not "done" if its PR cannot merge) → unresolved decisions. Show the stack topology and the merge order.

  **Verify the sibling overlap you assumed at step 1.** Both diffs now exist: `comm -12` the file lists, `git merge-tree` their merge base. One overlap claim carried by both tickets turned out to be seven shared files conflicting in three. One command — and report merge order only when it actually matters.

  **Collapse the follow-ups across units before reporting.** The raw sum is accurate and useless: "82 follow-ups" reads as debt, where "8 tickets, 6 one-liners, 5 questions, 13 closes" reads as a plan — same information, one of them actionable. Three collapsing mechanisms are structural to a fleet, not incidental: **the same finding from two lanes** (lanes cannot see each other's buffers, so duplication is guaranteed), **items a sibling resolved in-flight** (a hand-off written at hour 2 is stale by hour 9), and **documented-not-defects** recorded so a false claim is not re-inherited. Filing the raw list produces duplicate tickets for one defect, and tickets for work already done. Separate *needs a decision* from *needs work* — product questions are not backlog, they block it — and cluster survivors by theme, not by originating lane. Report both numbers, raw → collapsed. **Nothing consumes those buffers as a set, and you are the only actor that can.**

  Nothing merged; the tracker is untouched after step 0. Then run **`/capture-learnings` once** over the aggregated `<run>/learnings.md`: you're the interactive session again, so route and **dedup across all units in one pass** (3 units, same gotcha → one issue). The fleet stresses the flow hardest — escalations, drift, gate failures across N units — so it's the highest-signal source of flow learnings; this is where they land instead of dying with the worktrees.

## Decisions → PR body + ADRs
Every non-trivial decision (autonomous **and** escalated), with the **rejected** options, must be preserved so an unattended run never silently bakes in a choice. In this flow that record is the **PR body and ADRs**, not a committed log: keep an ephemeral per-unit decision list in `.work/` during the run, and `verify-build` promotes it into each unit's PR body (and into an ADR when the decision is hard-to-reverse **and** surprising **and** a real trade-off).

## run.yaml (ephemeral, gitignored)
```yaml
runId: multi-...
createdBaseSha: <pinned origin/default>
flags: { gateDesign: false, noPr: false, serial: false, maxParallel: 2, keepWorktrees: false }
deps: [ { child: B, parent: A } ]
units:
  - { id: A, wave: 0, worktree: <path>, worktreeCreated: false, branch: A-slug,
      base: <sha | parent-branch>, stackParent: null, designHeavy: true,
      designResolved: false, resolvedBase: null,
      step: build, status: in_progress, prUrl: null }   # step: pending|start|design|plan|build|verify-build|done
```
Orchestrator is the **sole writer** of `run.yaml`; agents write only `units/<id>.state.yaml`. `step` + `status` + the presence of per-slice commits determine where to resume.

## Principles (lessons baked in)
- **The orchestrator owns what no lane can see** — numbering, cross-lane dedup, base drift, sibling overlap, provisioning, addressing, the diamond merge. Each is invisible from inside a unit *by construction*, so none can be delegated by writing a better brief.
- **Recon is a hint, not a fact.** Compute anything base-sensitive against the **pinned BASE** (`git show <BASE>:<path>`), never a working-dir grep whose HEAD drifts from it, and hand it down as *"confirm this still reproduces at your base — it may be inherited from an earlier same-wave lane."* Stale-but-plausible recon makes an agent confidently redo inherited work.
- **Off the freshly-fetched default branch, verified by you.** Never trust an agent's ahead/behind ("74 ahead" was really 74 *behind*). `--dry-run` previews the resolved bases.
- **Tracker once, then never** — the run is self-contained and resumable.
- **Deps in run.yaml** (from `--deps` / one question), not tracker links.
- **Parallel by wave (capped), sequential across deps;** stacked children wait for the committed parent.
- **Mind the two axes.** Each unit's `build` may itself parallelize independent slices — the across-unit and within-unit axes **multiply**, so keep `--max-parallel` conservative and respect the host repo's sandbox/disk limits.
- **Never clobber a dirty worktree; tear down only what this run created.**
- **Resumable** via run.yaml + idempotent steps + per-slice commits.
- **Read a gate's verdict the way [EVIDENCE.md](../EVIDENCE.md) says to**, and require the same of every lane — a fleet multiplies both the number of instruments and the number of ways each one can be green about nothing.
- **Ready-for-review PRs; push is the last step; nothing merged; the tracker is never transitioned.**
- **No silent decisions** — autonomous and escalated alike ride into the PR body / ADRs with their rejected options.
- **Resolved designs make the grill a second pass** (step 4) — the seam that makes a design-multi → start-multi handoff unattended with no special mode to maintain.
- **Learnings survive teardown** (steps 3, 6, 8). Per-unit capture would race on issue-filing and die with the worktree, and the fleet is the richest learning source — so it cannot be the one flow that drops them.
