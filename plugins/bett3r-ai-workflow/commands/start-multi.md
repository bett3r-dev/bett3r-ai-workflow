# /start-multi — parallel delivery across worktrees

Drive a **list of work units** through the standard flow in parallel, isolating each in its own git worktree. You (the main session) are the **orchestrator**: you dispatch, verify git state with your own commands, collect escalations, and resume. You do **not** implement.

Run state lives in `.work/multi/<run-id>/run.yaml` — ephemeral, gitignored, and the **resumable** source of truth. Re-running the same set resumes it.

## Argument: $ARGUMENTS
Work-unit ids (+ optional descriptions), then flags.

| Flag | Effect |
|---|---|
| `--deps "C:P,..."` | Dependencies (child stacks on parent). The only dep source besides asking once. |
| `--dry-run` | Print the wave / worktree / branch-base plan; cut nothing. |
| `--max-parallel N` | Cap concurrent unit agents (default conservative — see Principles). |
| `--no-pr` | Stop after local per-slice commits; don't push / open PRs. |
| `--gate-design` | Pause after `design` on **every** unit (default: only design-heavy ones). |
| `--serial` | No cross-unit parallelism; run each unit's pipeline yourself, dispatching the real `executor`/`verifier`/`test-runner` agents. The rigor path. |
| `--keep-worktrees` · `--fresh` · `--run-id <id>` | Teardown / resume-state controls. |

## Per-unit pipeline
`start → design → plan → build → verify-build` (the standard flow, unattended). Each unit ends at a pushed **ready-for-review** PR whose body is the record. When a unit's ticket carries a `design-multi:resolved:vN` block (see step 0), its `design` step still runs — but the answers are already in the ticket, so it acts as a **verification second pass** that escalates only on code drift (step 4).

## Steps

**0 — Acquire & snapshot (the only tracker touch).** Resolve `run-id` (default `multi-` + sorted ids). If `run.yaml` exists and not `--fresh` → **resume** (skip to step 4). Else fetch each unit's content from the tracker **once**, snapshot it into the run dir (agents read the snapshot, never the tracker again). Pin the base: `git fetch origin`; `BASE=$(git rev-parse origin/<default-branch>)`. Mark design-heavy units (description markers, or `--gate-design`). **Detect a `design-multi:resolved:vN` block in the snapshot — grep the token, which is emitted both as an HTML comment and as a visible inline-code line, because some trackers strip comment nodes. If present, mark the unit `designResolved` with its `resolvedBase` — such a unit is *not* design-heavy (its human interview already happened in `/design-multi`).** This reader knows `:v1` and `:v2`; a `:vN` it does not know is unparseable — escalate rather than guess at a newer shape. **From `:v2` the block carries `status=ready | deferred | blocked | umbrella`: skip anything not `ready` and log why** (a `:v1` block has no field and is read as `ready`). Multi-ticket design runs routinely yield deferrals, units blocked on human-supplied secrets, and umbrella parents with no net-new code; picking one up unattended burns a lane and can open a bad PR. Write `run.yaml`, all units `pending`.

  **Snapshot without re-reading.** A resolved-design block runs ~10k tokens; fetching it into context and then re-emitting it verbatim through a write tool makes you pay twice, before a single agent starts, on exactly the well-resolved tickets this flow most wants. Write from the raw response (a scripted fetch straight to `units/<id>.ticket.md`). **Your job here needs a few lines, not the block**: the marker and its `base=` sha, the summary, the repos touched. Reading the block is the unit agent's job.

  Then derive, per unit, four things no lane can compute for itself — each cheap, each mechanical, each the difference between "trust the ticket" and "re-derive from symbols":

  - **Drift, per unit — not per run.** `git diff --stat <resolvedBase>..<BASE> -- <that unit's named files>`, marked `none | lines | structural`. One run-level note cannot express what is routinely true: zero drift on two surfaces and +1248/−732 across 31 files on a third.
  - **A runner + glob map.** For each unit: `surface → runner → include/exclude globs → can this runner see this unit's paths, y/n`. Resolve to the **glob**, not just the runner — "vitest runs this package" is worthless when `include` is `*.test.ts` only and the suites are `.test.tsx`. Each dispatch carries its own row, and a unit whose paths no runner collects must say so rather than let a green count imply coverage.
  - **The repo each unit belongs to** (see the unit kinds below), and its own base — a cross-repo unit's base is not `BASE`.
  - **The host repo's own build/test preconditions** — `CLAUDE.md`, and **every** file in `.claude/rules/` regardless of its `paths:` frontmatter. Path-gating is a context-loading optimisation, not a statement about relevance: the one moment a build precondition is needed is worktree-prep, when no matching file is in context and the rule structurally cannot fire. That is how a repo documented its own trap correctly and every run kept hitting it.

  Finally, **re-resolve every PR the resolved designs cite** (`gh pr view <n> --json state`). A design's PR-state claim is hours or days stale by dispatch, and a `MERGED` stack parent is a **base correction** — retarget that unit at the default branch — not an escalation. Phrase every tracker/branch fact you hand down as *"verify at BASE whether X"*, never as an asserted fact; your own recall is the least reliable input in the run.

  **Three unit kinds, because "unit == a worktree of the host repo" is not always true.** A **standard** unit is host-repo work with a build loop. A **multi-repo** unit needs checkouts of two or more repos, one of them primary (where the branch and PR live). A **cross-repo / no-build** unit has *zero* host-repo changes — its work lives elsewhere, often already committed — so it allocates no host worktree, its pipeline collapses to the landing tail (gate → push → PR), and `worktreeCreated: false` always. Record `repo:` and `runner: agent | orchestrator` per unit in `run.yaml`. The deciding test for the last kind, stated plainly: **if the target repo is outside the session's working directories, an unattended agent cannot complete outward-facing steps there — you run it.** Mixed-repo fleets are the normal shape of "land the deferred work from PR #X", not an exotic case; without a name for it the vocabulary pushes toward cutting a pointless branch and dispatching an agent whose first write blocks forever.

**1 — Deps → waves.** Populate deps from `--deps`, or ask **once** if >1 unit — but **read the resolved blocks before you re-interview.** A resolved block is an interview transcript, and it routinely settles file overlap in writing ("no shared files, safe in parallel"). Where every unit is `designResolved` and the blocks speak to overlap, derive `deps` and write a `depsRationale` quoting them; ask only about the units the blocks do not cover. Every question the blocks already answered is a place this handoff leaks back into human time. Treat the derivation as a **hypothesis about diffs that did not exist when it was written** — step 8 verifies it. Topologically sort into waves; detect cycles → stop. Never read tracker links (their direction/coupling is unreliable).

**2 — Worktrees & branches: `install` is not `ready`.** A worktree is ready when the artifacts its own tests import exist on disk — not when the checkout is cut. Per unit (wave order): pick a **clean** worktree (reuse an unassigned one, else `git worktree add --detach`); one unit per worktree; **never a dirty worktree**. Branch base: independent → `BASE`; stacked → the parent's committed tip. Cut the branch, then **verify the base yourself** — independent: `git -C <wt> rev-list --count HEAD..origin/<default>` must be `0`; stacked: `git -C <wt> merge-base --is-ancestor <parent-tip> HEAD`. `--dry-run` prints the resolved plan and stops here. Then provision, all of it before any agent is dispatched:

  - **Install *and* build.** Prefer the recursive script (`build:all`, `build --recursive`, `turbo build`) over a bare `build`, which in a `tsc --build` monorepo may emit only one module format while the workspace's `exports.import` points at the other. Workspace deps resolving through a gitignored `build/` are absent in every fresh worktree, so this hits **every unit of every run** — presenting as "40 of 57 files collected zero tests" or `Failed to resolve entry for package`, which reads as a broken baseline rather than a missing step. It is fixable once here, or paid N times in parallel by agents who each get it wrong independently.
  - **Archive, don't delete, a reused worktree's `.work/`.** The dangerous files are exactly the ones the flow reads back — `design.md`, `slices.yaml`, `pr-body.md`, `decisions.md` — and a populated `slices.yaml` gives a lane every reason to build a different ticket. Prior contents are distinguishable from current ones **only by mtime**; `.work/` is gitignored so `git status` is clean and the staleness is invisible. Move it into the run dir rather than `rm -rf`: those buffers include `learnings.md`, which step 6 exists to rescue. Also **re-emit composite `build/*.d.ts`** — a switched branch leaves phantom `TS6305` cascades that the transpile-only build never surfaces. Belt-and-braces worth its one line: **stamp the ticket id into the first line of every scaffolded `.work/` file**, and tell agents to check that line first, so a missed scrub is caught on the first read instead of on inspection.
  - **Lay a multi-repo unit's worktrees out by *repo*, not by ticket** — `<RUN>/wt/<unit>/<repo>` — so the relative path between two checkouts matches the relative path between their canonical clones. Naming by ticket silently breaks every `portal:` / `file:` / `link:` / relative `workspace:` specifier the repos already have between them, and it is a hard block, not a slowdown: `yarn install` dies at resolution with `Manifest not found`, which points at a manifest rather than at the layout. Check each root manifest for specifiers pointing outside the worktree and verify they resolve, at cut time.
  - **Give each unit its own scratchpad subdirectory** (`<scratchpad>/<unit-id>/`) and pass *that* path in the brief. Worktrees are isolated; the session scratchpad is not — every lane inherits the same root, and one lane's `pr-body.md` has silently clobbered another's. The exposure grows as the brief standardises filenames.
  - **Write `.work/known-baseline-failures.md`** per unit — the pre-existing typecheck/test failures at the pinned base, and **how they were captured** — so no lane re-derives it. Capture on a **freshly built** tree: unresolved-dependency errors cascade into ordinary-looking `TS2345`/`TS2322` that are indistinguishable from real ones by inspection, so "filter out the known-noise code and trust the remainder" is not a safe protocol — the remainder is contaminated by the same cause. (Measured: `134 × TS6305 + 24 "real"` → `0 + 1` after re-emitting declarations.) Incremental checkers under-report on a second run; clear the incremental state for a comparable count. A wrong shared baseline is worse than none — lanes either chase errors that are not theirs or, in the dangerous direction, treat real new errors as pre-existing cover.

  **Size `--max-parallel` by memory, not cores, and say so.** Past some N the fleet falls off a **cliff**, not a slope: the same build measured 95 s alone and >38 min under load at swap 31.9 GB of 33.8. Scope the per-unit gate to the touched packages (a server-side unit rarely needs the web bundles) and serialize `generate-all`-class steps behind a lock. Contention is also the mechanism behind the 600 s deadlock, and a starved lane is easy to misread as a hung one — so log the load average / swap when a gate overruns.

**3 — Dispatch.** Process **waves in order**; within a wave launch background agents up to `--max-parallel` (queue the rest). A stacked child waits for its parent's **commit**. Each agent is worktree-scoped, runs the per-unit pipeline against its worktree, and writes **only** its own `<run>/units/<id>.state.yaml`. **Single-writer rule:** only you write `run.yaml` (aggregate the per-unit files) — this prevents concurrent-write races. **Failure isolation:** a unit that fails unrecoverably is marked `failed`, the others continue, and any unit stacked on it becomes `blocked`. **Learnings, not issues:** an agent that hits friction in the *flow itself* (a gate that misfired, a skill that misled, a step that fought the grain) `record`s it to its worktree's `.work/learnings.md` — **buffer only**. Never `/capture-learnings` inside an unattended agent: it files GitHub issues one-confirm-each and dedups against the backlog, so N agents racing it produce duplicate / wrong-repo issues. The orchestrator rescues the buffers before teardown (step 6) and captures once at the end (step 8). (`--serial`: run each unit yourself with the real executor/verifier/test-runner agents — full rigor, no cross-unit parallelism.)

  **Address every message; never resolve a recipient from recall.** Write `<run>/agents.yaml` (`unitId`, `agentId`, `worktree`, `dispatchedAt`) the moment each agent launches, resolve the recipient from that file before every `SendMessage`, and **lead every message with `TO: <TICKET-ID>`**. You reason in ticket ids; the harness addresses opaque ids; at four-plus live lanes that mapping is not memorable, and reconstructing it from dispatch order has misrouted two corrections in one run — silently in both directions, the wrong lane getting noise and the right one never receiving a directive without which its own AC could not hold. Fleet contract: **if a directive's ticket id is not yours, do not act — record the misroute and report it.**

  **A directive carries the constraint, never the expression.** Your directives inherit your authority: an executor weighs its own design choices against the code but treats a *prescribed expression* as settled, so implementation-shaped detail routes around the very judgment the dual gate exists to apply. One `saleTime: data.date ?? existing.saleTime` was implemented faithfully and double-billed a metering period; the correct directive was *"`saleTime` is the bucketing key and must not move when an edit arrives — `date` is mutable"*, which an executor would have satisfied **and tested**. Say the invariant and the evidence; let the executor derive the code. The contract's other half is symmetrical and currently missing by omission: **a directive from the orchestrator is an input to the lane's judgement, not a settled decision — if it contradicts the code, the code wins and the lane says so.** When one of your directives *is* caught by a lane's gate, the PR records the provenance; the record should show the gate working, not silently absorb it.

  **Allocate anything monotonically numbered — ADR numbers above all.** Lanes self-numbering from their own branch collide by construction: three lanes have picked the same `ADR-057`, different filenames, no git conflict, a clean merge hiding it. Hand each lane its number **in the initial brief** (waiting until a lane wants one means it has already started writing) and require it to report back **claimed** or **released**, or reserved-but-unused numbers leave permanent holes. Derive the range from every ref and every sibling branch — `git ls-tree <branch> -- <adr-dir>` sees sibling worktrees' unpushed ADRs — never from a remembered number: a fleet contract seeded from a stale one collided on its first slot. An absolute number in a dispatch prompt is a claim with a very short shelf life, so `/verify-build` re-checks against the merge target regardless. Ask the lane to prefer **amending an existing ADR** where one already covers the ground.

  **Nested-agent mechanics, which invert one level down.** Unit agents dispatch children **synchronously via `Agent` with `run_in_background: false`** — only `Agent` honours it; `SendMessage` cannot be made synchronous, so a lane that resumes a child via `SendMessage` is **idle, not working**, and sits until you resume it. A fix pass on an existing child must therefore be a fresh `Agent` dispatch, accepting the lost context, never a cheaper `SendMessage`. The asymmetry is worth stating outright because it is counter-intuitive: **the same call is safe for you and unsafe for a lane** — your backgrounded resumes notify the top-level session normally. Correspondingly, treat every **grandchild** completion as *"resume the owning parent"*, resolved through `agents.yaml`.

**4 — Collect & resume. Git is the primary resume signal; the state file is a hint.** Two of the three signals `run.yaml` describes can go stale in the same direction and for the same reason — a lane honours "update your state after each pipeline step" literally, and `/build` *is* one step containing N slices. A unit has read `step: plan, commits: []` while its branch carried two committed slices and a third verified. So **cross-check `git log origin/<default>..HEAD` against the flags** whenever you verify build-complete, and always before cutting a stacked child — that is the moment a parent's bookkeeping stops being its own business.

  **A stall detector needs a terminal state and a positive control.** Units that reached `passed`/`failed` are excluded from staleness checks; without that, a finished lane and a dead one produce identical signals — no writes, no transcript, no commits — and the watchdog cries wolf exactly when the run is going well, then gets muted right before it would have been useful. Validate the detector against a directory you just wrote to before trusting any negative: a detector never seen to fire is not evidence of calm. (`find -newermt '<relative>'` matches **nothing** on BSD/macOS, silently — use `-mmin -N`.) The two stop shapes need opposite responses and look identical in the notification: **completed + ~0 tool uses + untouched branch** is starvation, safe to re-dispatch; **completed + real work + a "standing by" final message** is a deadlock needing a corrective resume.

  **A grandchild's report is not addressed to you.** A `verifier` / `executor` / `test-runner` notification from inside a unit's `/build` loop reaches your session, and its "the orchestrator may commit" means the **unit agent**, which already has the result directly. Do not act on it, do not relay it, do not write into that unit's worktree. Read it as progress only. Volume here scales with **slices × units** — the two axes that already multiply — so at any real fan-out these verdicts will bury the signals that are genuinely yours: a unit escalating, and a unit finishing.

  Aggregate per-unit state into `run.yaml`. Resume any `in_progress` (dead agent) or escalated unit from its next incomplete step — the flow is idempotent: slices already `passes: true` and committed are skipped. **Batch escalations** and present them together as a numbered list — recommendation first, one line of *why* each escalated. Do **not** use `AskUserQuestion`; the user answers free-form. A **design-heavy** unit stops after `design` — surface its `.work/design.md` for review before it proceeds to `plan`. A **design-resolved** unit is not gated: it runs `/design` **as normal**, but because the ticket already carries the resolved decisions, the grill **verifies rather than re-derives** (see `/design`) and flows straight to `plan` with nothing to ask. It escalates only if the code has **drifted** enough to re-open a fork the resolved block doesn't answer — batched like any other escalation. The resolved block turns the ordinary design step into a cheap unattended **second pass**; there's no separate mode to maintain here.

**5 — Commit & PR.** Per passed unit, ensure the per-slice commits are in place; then (unless `--no-pr`) run `verify-build` to open the PR **ready for review** — `--base <parent-branch>` if stacked, else the default branch. Record `prUrl`. A stacked child wave may begin once its parent is committed.

  **Re-check the pin before `verify-build`, every time.** `git fetch origin` and compare `origin/<default>` against `createdBaseSha`. Nothing else re-checks it, so the last unit to finish silently eats whatever landed during the run — and the cost is asymmetric, arriving with the work done, the gates green and the PR declared ready. If it moved, name the overlapping files per unit (`git merge-tree` pinpoints them in one command) and record the drift in `run.yaml` so a resumed run inherits it. Runs are long by construction; an external merge is normal collaboration, and the defect is only that nobody looked.

  **You own a diamond base.** When a unit depends on two sibling parents, the two-parent merge is yours, not the child's — a base that does not compile is a broken foundation whose failures surface deep inside the child. Recipe: generated/codegen files → `git checkout --theirs` then re-run the generator, never hand-merge; hand-authored additive files → splice **complete** units (apply the sibling's additive hunks), never a marker-strip, which breaks on array tails and interleaves two partial blocks at their shared prefix; then build and drift-check the base **green**, and check for `*.orig` residue before committing — a `.ts.orig` is not compiled, so it passes every gate invisibly.

  **A child cut early is stranded on a base its parent then fixes.** Cutting at build-complete rather than PR-open is the right throughput call, but `verify-build` exists precisely to find defects no single-slice review can see, and every one of those lands *after* the cut. Record `parentTipAtCut`; require the child to **forward-merge the parent after the parent's `verify-build`**, and again immediately before opening its PR (a PR base is a moving ref, so a stale local base makes the child's diff misleading too). Better: diff `parentTipAtCut..parentHEAD` yourself and **tell the child what changed and why it matters to its work** — a child cannot be expected to notice that a commit on its parent's branch invalidates an assumption inside its own slice. The missing fix does not surface as a failure: one child's deterministic test would have gone green over the live race the parent had just closed.

**6 — Rescue learnings (before teardown).** Aggregate each unit's worktree buffer `.work/learnings.md` into the run dir (`<run>/learnings.md`), tagged by unit; fold in any flow-friction you hit while dispatching / resuming. This **must precede teardown** — the buffers live in the worktrees and step 7 deletes them. (This subsumes `verify-build`'s per-unit "run `/capture-learnings`" nudge, which an unattended agent can't action; the fleet defers it here.)

**7 — Teardown.** Remove only worktrees **this run created** whose branch is pushed (or whose unit is terminally `failed` and acknowledged). **Never** remove a pre-existing or dirty worktree. Skip if `--keep-worktrees`.

**8 — Report & capture.** Per unit → branch (+ base/stack) → step reached → **PR URL *and* its `mergeable` state** (a unit is not "done" if its PR cannot merge) → unresolved decisions. Show the stack topology and the merge order.

  **Verify the sibling overlap you assumed at step 1.** Now that both diffs exist, `comm -12` the two file lists and `git merge-tree` their merge base. A resolved design's overlap claim was written before either diff existed, and one such claim — carried by both tickets — turned out to be seven shared files conflicting in three. It costs one command, and merge order should be reported only when it actually matters.

  **Collapse the follow-ups across units before reporting.** The raw sum is accurate and useless: "82 follow-ups" reads as debt and sets the user's posture toward the whole run, where "8 tickets, 6 one-liners, 5 questions, 13 closes" reads as a plan. Three collapsing mechanisms are structural to a fleet, not incidental — **the same finding reported by two lanes** (lanes cannot see each other's buffers, so duplication is guaranteed), **items a sibling resolved in-flight** (a hand-off written at hour 2 is stale by hour 9), and **documented-not-defects** recorded so a false claim is not re-inherited. Filing the raw list would produce duplicate tickets for one defect and tickets for work already done. Separate *needs a decision* from *needs work* — product questions are not backlog, they block it — and cluster survivors by theme, not by originating lane; the lane is an artifact of how the work was parallelised and is not how anyone will schedule the fixes. Report both numbers, raw → collapsed. The per-lane buffer is right; the gap is that **nothing consumes those buffers as a set, and you are the only actor that can.**

  Nothing merged; the tracker is untouched after step 0. Then run **`/capture-learnings` once** over the aggregated `<run>/learnings.md`: you're the interactive session again, so route and **dedup across all units in one pass** (3 units, same gotcha → one issue). The fleet stresses the flow hardest — escalations, drift, gate failures across N units — so it's the highest-signal source of flow learnings; this is where they land instead of dying with the worktrees.

## Decisions → PR body + ADRs
Every non-trivial decision (autonomous **and** escalated), with the **rejected** options, must be preserved so an unattended run never silently bakes in a choice. In this flow that record is the **PR body and ADRs**, not a committed log: keep an ephemeral per-unit decision list in `.work/` during the run, and `verify-build` promotes it into each unit's PR body (and into an ADR when the decision is hard-to-reverse **and** surprising **and** a real trade-off).

## run.yaml (ephemeral, gitignored)
```yaml
runId: multi-...
createdBaseSha: <pinned origin/default>
flags: { gateDesign: false, noPr: false, serial: false, maxParallel: 2, keepWorktrees: false }
deps: [ { child: B, parent: A } ]
units:
  - { id: A, wave: 0, worktree: <path>, worktreeCreated: false, branch: A-slug,
      base: <sha | parent-branch>, stackParent: null, designHeavy: true,
      designResolved: false, resolvedBase: null,
      step: build, status: in_progress, prUrl: null }   # step: pending|start|design|plan|build|verify-build|done
```
Orchestrator is the **sole writer** of `run.yaml`; agents write only `units/<id>.state.yaml`. `step` + `status` + the presence of per-slice commits determine where to resume.

## Principles (lessons baked in)
- **The orchestrator owns what no lane can see.** Numbering, cross-lane dedup, base drift, sibling overlap, provisioning, addressing, and the diamond merge. Each is invisible from inside a unit *by construction*, so none of them can be delegated by writing a better brief — and every one has shipped a defect when it was.
- **`install` is not `ready`, and recon is not fact.** Provision worktrees fully before dispatch; compute base-sensitive recon against the **pinned BASE** (`git show <BASE>:<path>`), never a working-dir grep whose HEAD drifts from it, and frame it as *"confirm this still reproduces at your base — it may already be inherited from an earlier same-wave lane."* Stale-but-plausible recon is the worst kind: it makes an agent confidently redo inherited work.
- **Off the freshly-fetched default branch, verified by you.** Never trust an agent's ahead/behind ("74 ahead" was really 74 *behind*). `--dry-run` previews the resolved bases.
- **Tracker once, then never** — the run is self-contained and resumable.
- **Deps in run.yaml** (from `--deps` / one question), not tracker links.
- **Parallel by wave (capped), sequential across deps;** stacked children wait for the committed parent.
- **Mind the two axes.** Each unit's `build` may itself parallelize independent slices — the across-unit and within-unit axes **multiply**, so keep `--max-parallel` conservative and respect the host repo's sandbox/disk limits.
- **Never clobber a dirty worktree; tear down only what this run created.**
- **Resumable** via run.yaml + idempotent steps + per-slice commits.
- **Ready-for-review PRs; push is the last step; nothing merged; the tracker is never transitioned.**
- **No silent decisions** — autonomous and escalated alike ride into the PR body / ADRs with their rejected options.
- **Resolved designs make the grill a second pass.** A ticket carrying a `design-multi:resolved:vN` block (from `/design-multi`) runs `design` as normal, but the answers are already present — the grill verifies rather than asks and flows through; only code-drift that re-opens an unanswered fork escalates it. This seam makes a design-multi → start-multi handoff unattended without a special mode.
- **Learnings survive teardown.** Unit agents `record` flow-frictions to their buffer; the orchestrator **rescues those buffers before teardown** and runs one batched `/capture-learnings` at the end. Per-unit capture would race on issue-filing and die with the worktree — the fleet is the richest learning source, so it can't be the one flow that drops them.
