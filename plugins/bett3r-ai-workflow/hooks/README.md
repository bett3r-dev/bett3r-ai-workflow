# Hooks

## How this plugin declares a hook

`hooks/hooks.json` at this exact path is loaded automatically for every enabled plugin; `plugin.json`'s `hooks` field is for additional hook files only, and pointing it back here is an error. Shape:

```jsonc
{ "hooks": { "<Event>": [ { "matcher": "<tool>", "hooks": [ { "type": "command", "command": "sh", "args": ["${CLAUDE_PLUGIN_ROOT}/hooks/<file>"], "timeout": 5 } ] } ] } }
```

`${CLAUDE_PLUGIN_ROOT}` is substituted in `command` and in each `args` element, and only for plugin hooks; `${CLAUDE_PROJECT_DIR}` is exported into the hook's environment, which is what every script here reads. `args` is the exec form: no shell re-parse, so a plugin path with spaces cannot break the invocation. `matcher` selects on the tool name and nothing else; there is no per-directory matcher, so every hook here runs in every repo where the plugin is enabled, and the first thing each script does is one cheap check that exits 0 wherever the hook does not apply.

## blueprint-pending.sh (`UserPromptSubmit`)

Injects one line, `blueprint: N pending (seq A→B)`, while the user has unsynced semantic edits on the BLUEPRINT design board. Telemetry, never a trigger; the rule for reacting to it is `skills/blueprint-pending/SKILL.md`. Line 2 is `[ -f "${CLAUDE_PROJECT_DIR:-.}/.blueprint/ops.jsonl" ] || exit 0`. Every path exits 0, because a `UserPromptSubmit` hook that exits 2 erases the user's prompt; with `wc` and `awk` missing it prints nothing. Scanning is linear in the part of the feed the cursor has not bounded, and a hit of the 5 s timeout costs one prompt's telemetry, never the prompt.

## blueprint-session-channel.sh (`SessionStart`)

Prints one instruction, to open the board's session channel with `Monitor({ ws: { url: 'ws://127.0.0.1:<port>/api/blueprint/ws' }, persistent: true })`, so the board's *Ask Claude* button can reach an idle session from t=0, resumed sessions included. Its gate exits 0 unless the checkout's git dir holds a `/blueprint connect` record (`blueprint-connection.json`, found by a `read` of a linked worktree's `.git` file, or under `GIT_DIR` when set) or there is a `.blueprint/`; with a usable record it skips the local table below and prints the branch reminder and the `blueprint listen` instruction in the states the hook's header tables (BP-277). Without a record it speaks in exactly one state: a board answering `GET /api/blueprint/status` on `${BLUEPRINT_BOARD_PORT:-3727}`, serving this checkout, reporting `sessions: 0`. Nothing on the port, a board for another checkout, `sessions >= 1`, no `sessions` field, no `curl`: all silent, exit 0. A board started later in the session is recovered by the `blueprintSessionChannel` notice `blueprint-mcp` attaches to its tool results.

## lane-git-guard.sh (`PreToolUse`, matcher `Bash`)

In an unattended lane, blocks the git commands that discard or shelve the working tree. A lane is any checkout holding `.work/lane.yaml`, the brief the provisioner writes, and the checkout a command acts on is not always the project dir (a fleet lane is a subagent of the orchestrator's session and reaches its worktree through `cd` or `git -C`). So the hook reads the event JSON on stdin (line 2; a payload with no `git` in it exits there on a glob match), takes `tool_input.command` and `cwd` from it, tokenises the command with `;`, `|`, `&`, `(`, `)`, a backtick and a newline as separators, and looks for the brief in the cwd, in `CLAUDE_PROJECT_DIR`, and in every path after `cd`, `-C` or `--work-tree` (relative paths resolve against the cwd). When one of them holds the brief and the command carries `git stash` (except `create`, `list`, `show`), `git reset --hard`, `--merge` or `--keep`, `git checkout --`, `.`, `-f` or `--force`, `git switch -f`, `--force` or `--discard-changes`, `git restore` or `git clean -f`, it exits 2 with one line on stderr naming the command and the alternative, `git stash create` plus `git diff <object>`. Everything else exits 0, and nothing is ever written to stdout. The match is on the command's own tokens, so the words inside a quoted string or a description do not match; a heredoc body line starting with `git stash` does.

## blueprint-precompact-note.sh (`PreCompact`)

Asks a Blueprint design run for its note before compaction (ML-1, F14). Claude Code appends a PreCompact hook's stdout, on exit 0, to the compaction's custom instructions, and the agent gets no turn before the summary; so the one line it prints asks the summary to keep what the run was doing, the dead ends, the person's preferences and the session id, and to end with the instruction to call `WriteNote` (`mcp__blueprint__WriteNote`) with them before anything else if the agent's tools include it, and otherwise to keep the note in the summary (a Blueprint server older than `WriteNote` has no such tool). Line 2 is the gate: a project dir matching `*.blueprint-worktrees/?*`, the worktree Steward runs a design agent in. Everywhere else, a `.blueprint/` or a `/blueprint connect` record included, it prints nothing. Every path exits 0, because a PreCompact hook that exits 2 blocks the compaction.

## blueprint-capture.sh (`Stop`, `SessionEnd`, `SessionStart`) and `bin/blueprint-send`

Captures a conversation with Claude outside Blueprint into Blueprint's memory, only on its person's say-so (ML-1, F28) and after the secret check (F17). Line 2 is the gate: `BLUEPRINT_CAPTURE_REPOSITORY`, the repository's name in Blueprint, which the repository sets in its checked-in `.claude/settings.json` `env`; unset, the hook does nothing else. Each person sets `BLUEPRINT_CAPTURE` to `off`, `ask` (the default, and what any other value reads as) or `always`, in `.claude/settings.local.json` `env` or the shell. `off` does nothing.

In `ask`, the first `Stop` of a session whose person has a Blueprint host and a token the hook can read blocks once (`{"decision":"block"}`) with an instruction for the agent to ask "Send this conversation to Blueprint's memory?" with a one-line summary. A yes runs `blueprint-send --consent --session-id <id>`, which records it and sends nothing yet; that session's `SessionEnd` then sends the whole transcript, every later turn included (Blueprint replaces a conversation sent again, so a session sent earlier with `/blueprint-send` is sent again whole too, each message the way its own choice says and every message no choice covers checked again; after `--text` not at all, the edit being final). A no runs nothing, and nothing leaves the machine. `Stop` is the only hook that gives the agent a turn and `SessionEnd` runs after the conversation is over, so the ask comes at the first end of a turn and the send at the close. Later Stops of that session, and a Stop already continuing from a Stop hook, are silent. A run nobody answers is never asked, since the question would replace its final answer: `CLAUDE_CODE_ENTRYPOINT` `sdk-cli` (`claude -p`), `sdk-ts`, `sdk-py` or `claude-code-github-action`, a lane (`.work/lane.yaml`), or a Steward design run (`*.blueprint-worktrees/*`). Without a readable token (the `blueprint` CLI keeps a sign-in in the OS keychain unless `blueprint login --store file`, and a hook cannot read the keychain without risking a GUI prompt) it does not ask, and says once a session, in one line on stderr, to run `blueprint login --host <host> --store file` or set `BLUEPRINT_ACCESS_TOKEN`.

In `always`, `SessionEnd` sends unasked. When a `SessionEnd` send finds a secret, nothing is sent and the warning with its three ways on is left as a pending record of the repository, under `$XDG_STATE_HOME/blueprint/capture/pending/` (else `~/.local/state/...`), never in the repository. The next `SessionStart` in that repository, unless it is a run nobody answers or the person's capture is `off`, prints it once for the agent to tell the person, who redacts, edits or sends anyway.

`blueprint-send` (the `bin/` launcher of `hooks/blueprint-capture.py send`, which `/blueprint-send` runs) renders the transcript (prompts and replies in full; tool calls and tool output cut to 400 characters, the cut moved around a private key whose `-----BEGIN … PRIVATE KEY-----` header starts before it: a key with its own `-----END … PRIVATE KEY-----` marker is kept through that marker, so the secret check sees it whole, and one with no END marker of its own (none follows, or another key's header comes before it) is cut at its header's start, with nothing of it or after it kept, even in an output under 400 characters; no thinking, meta or system lines), posts it to Blueprint's `/secret-check` in pieces under 1 MiB that overlap by 16,384 characters (a secret shorter than that across a cut is found whole), and on a match prints "This looks like a secret" with the three ways on, `--redact`, `--text <edited file>` and `--anyway`, and exits 3 having sent nothing else. `--redact` replaces each match by a marker, a match that starts inside another extending that marker to its own end. A choice is by message. A `--redact` or `--anyway` covers the messages the person was shown when they chose (those of the last warning about the conversation, a record `shown-<id>` in the same state folder, one sha256 a transcript line, else every message at the send) that no earlier choice covers; an earlier choice is never re-decided. The send keeps each message's choice in the session's `yes-<id>`, which every later send of the conversation applies, `SessionEnd`'s included. A match counts as chosen only when it lies wholly inside chosen messages (the blank line between two of them included), and is then redacted if any of it lies in a message chosen for `--redact`, else sent as it is. Any other match blocks with the warning, which counts only those matches, and nothing is sent. An edited `--text` covers nothing. Otherwise it takes an upload grant, posts the bytes to the bucket with the grant's fields and their SHA-256 checksum, and names the object to `CaptureConversation` with the repository, the Claude session id, and the session `/blueprint connect` connected the checkout to. Host: `BLUEPRINT_HOST_URL`, else the connect record; token: `BLUEPRINT_ACCESS_TOKEN`, else the `blueprint` CLI's credentials file (`~/.config/blueprint/credentials.json`). Any failure (unreachable, no readable token, refused) is one line. The hook never blocks work and fails open: it exits 0 on every path, and its only block is the one ask.

## Tests

`sh scripts/test-hooks.sh` at the repo root covers all five: the pending count against fixtures produced by the real `@bett3r-dev/blueprint-store` (`scripts/fixtures/blueprint-pending/README.md`), the session channel against a stub board on an ephemeral port, the guard against synthesized `PreToolUse` payloads, the note before compaction run as `hooks.json` declares it against synthesized `PreCompact` payloads, the capture run as `hooks.json` declares it and `bin/blueprint-send` against a stub Blueprint (secret check with overlapping and multi-line rules, grant, bucket, capture) on an ephemeral port that logs every request, and the wiring in `hooks.json`.

## Fallback: installing a hook by hand

Not needed in a normal install. For a user who wants the pending count without enabling the plugin, add to `.claude/settings.json` in the repo being designed and copy `blueprint-pending.sh` to `.claude/blueprint-pending.sh`:

```jsonc
{
  "hooks": {
    "UserPromptSubmit": [
      { "hooks": [ { "type": "command", "command": "sh", "args": [".claude/blueprint-pending.sh"], "timeout": 5 } ] }
    ]
  }
}
```

`${CLAUDE_PLUGIN_ROOT}` is not available in `settings.json`, so the path is a real one, and a hand-installed copy does not update with the plugin. If both are installed the line appears twice; remove one.
