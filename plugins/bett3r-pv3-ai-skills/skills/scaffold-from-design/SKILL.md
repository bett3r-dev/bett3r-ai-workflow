# Skill: Scaffold From Design

The **mechanical pass**. Everything the design graph already determines — file paths, builder
wiring, event names, registration lines, and above all the **node ids the extractor will read
back** — is generated by a tested program instead of retyped. What is left is what the graph
cannot know, and that is what the `create-*` skills are for.

Run this **before** `create-policy` / `create-readmodel` / `create-schema`, not instead of them.

## Why a program and not a prompt

Not to save typing. To make the design converge.

`/design` proposes `sales_pol_buyer-invoice-preference-send-policy`. The ESAS extractor later
re-derives an id from whatever was actually written. Drift by one word in a label or a subdomain
and the proposal never flips to `satisfied` — the board reports a phantom artifact forever, and
nobody notices, because the code is fine. The scaffolder imports the id function the extractor
uses, so what it emits reads back as exactly what was proposed.

The second reason is placement. A policy in the wrong module compiles, passes its tests, ships,
and fails a guard later. The rule is mechanical (below), so it is computed, not remembered.

## Preconditions

| Need | Check |
|---|---|
| `.esas/design.json` exists | the unit ran `/design`; the file is per-unit and gitignored |
| `.esas/graph.json` is current | re-extract if the working tree has moved since the design |
| the slice names its design nodes | `designs:` in `.work/slices.yaml` — written by `/plan` |

If the slice has **no `designs:` field**, this slice delivers nothing from the design layer, or
the plan predates the field. Do not guess a node set from the slice title: scaffolding the wrong
artifacts is worse than scaffolding none. Say so and write by hand.

## Step 1 — Dry run, always first

```bash
npx esas-pv3-scaffold --repo "$PWD" --nodes <the slice's designs: ids, comma-separated>
```

Writes nothing. Prints what it *would* create, the fragments it will not write, and anything
blocked.

**Read the BLOCKED section before anything else.** Each entry is a question the graph could not
answer, and each one is a real gap — a new subdomain with no home yet, a policy whose target
handler does not exist, a command with no `handled-by` edge. **Surface these to the user rather
than deciding them yourself**: they are design questions wearing a code hat, and the board is
where they get answered. The scaffolder deliberately refuses to guess, and overriding that by
hand-placing the file discards the only signal that a decision is missing.

Exit codes: `0` nothing blocked · `1` the design or graph could not be read, or the slice names
an id the design no longer contains (a stale plan — re-check `slices.yaml` against the board) ·
`3` something was blocked.

## Step 2 — Write

```bash
npx esas-pv3-scaffold --repo "$PWD" --nodes <ids> --write
```

**Only files are written. Fragments never are.** A file is emitted only when its host file does
not exist, so this cannot overwrite anything — enforced by the `wx` open flag, not by a check.

## Step 3 — Place the fragments yourself

A fragment is code for a file that **already exists**: a new command inside an existing
aggregate's `.withCommands({…})`, a new event beside its siblings, the registration line in the
module `index.ts`. The tool prints the code, the imports, and a structural anchor; you place it.

This split is deliberate and is not a limitation to route around. The previous generation of this
tooling tried to merge generated code into edited files; its merge step degraded to "use the
generated one" and silently overwrote hand-written work. Nothing here opens a file it did not
create.

**Place every registration fragment.** An artifact nothing registers compiles, typechecks, and is
never wired to the event bus — it simply never runs, which looks exactly like a wrong projection.
It is the most likely way a scaffolded slice ends up looking finished while doing nothing.

## Step 4 — Fill what the graph cannot know

`EsasNode` carries no fields, so **none of this is derivable and none of it was guessed**. Every
generated file states its own list in a `STILL OWED` block; the `TODO(scaffold)` markers are the
line-level version of the same thing.

| Owed | Skill to open |
|---|---|
| schemas, event/command payload types, `friendlyName` | [`create-schema`](../create-schema/SKILL.md) |
| command handler bodies, invariants, idempotency, stream strategy | [`create-aggregate`](../create-aggregate/SKILL.md) + [AGGREGATES.md](../ddd-patterns/AGGREGATES.md) |
| policy handler bodies, fan-out, redelivery, dependency declaration | [`create-policy`](../create-policy/SKILL.md) + [POLICIES.md](../ddd-patterns/POLICIES.md) |
| projection bodies, queries, indexes, scope enforcement | [`create-readmodel`](../create-readmodel/SKILL.md) + [READMODELS.md](../ddd-patterns/READMODELS.md) |
| the slice's oracle test | [`create-tests`](../create-tests/SKILL.md) |

**Delete the `TODO(scaffold)` marker when you satisfy it**, and delete the `STILL OWED` block when
the file is complete. A scaffold banner left in finished code trains the next reader to ignore
banners.

## What it does and does not emit

Emitting nothing is not the same as having nothing to say — the table is the honest boundary, and
the right-hand column is where the work actually is.

| Design element | Emitted | You still write |
|---|---|---|
| `policy` | whole file + registration | handler bodies, dependency declaration, redelivery safety |
| `read-model` | whole file + registration | projections, queries, indexes, scope |
| `command` on an **existing** handler | fragment | the command schema, the handler body, stream/idempotency |
| `command` on a **proposed** handler | *blocked* | scaffold the handler first — order the slices so it exists |
| `event` | fragment | the event schema, the namespace registration, translations |
| `aggregate`, `system` | **nothing** | the whole file — use `create-aggregate` |
| schemas, tests | **nothing** | `create-schema`, `create-tests` |

## Placement, and why it is computed

> A policy belongs in the module of the aggregate its `createCommand` targets — **not** the module
> that emits its trigger event.

Resolved from the graph as `policy --issues--> command --handled-by--> handler`. Measured against
98 shipped policies in the reference repo this predicts the correct **module** for 92; one of the
six misses is grandfathered as a known violation in that repo's own placement guard, so where it
disagrees with the tree it disagrees the way the guard does.

The exact **subdirectory** is weaker — 70/95 — but always inside the correct module. So a
generated file states its confidence in the banner: `guard-enforced` means the module is settled
and a move within it is cheap; `inferred` (read-models, which no guard governs) means check it.
**A wrong module is a build failure; a wrong subdirectory is a `git mv`.** Do not treat the two as
the same finding.

## Re-running is safe, and is the point

The run is a **delta**: proposed graph minus extracted graph. Anything that already exists in code
is reported as `ALREADY REAL` and emitted again by nothing. So a mid-slice re-run after
re-extracting the graph is a legitimate way to ask "what is still outstanding?" — there is no
state file to get out of sync, because the two graphs *are* the state.

## Critical constraints

- **Never hand-place a blocked artifact to get past the block.** The refusal is the finding.
- **Never edit a generated file to change its id-bearing identity** (its export name, its label,
  its subdomain) without changing the design. The id is the convergence contract; drift there is
  invisible until the board reports a phantom.
- **Do not run it un-scoped (`--nodes` omitted) with `--write`.** That scaffolds the whole design
  delta into one commit of unreachable stubs — the thing vertical slicing exists to prevent.
- The scaffolder reads `.esas.config.json` for paths and package names, like every skill here.
