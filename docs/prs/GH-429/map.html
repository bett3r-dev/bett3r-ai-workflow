GH-429-F1 · GH-429 · decided (owner): B

Where the orchestrator's yield sits

The orchestrator is the last context that lives as long as the whole fleet. It can end and be re-dispatched, resuming from run.yaml. The question is at which boundary it is allowed to end.

  • a 7-unit fleet across 3 waves on one laptop
  • a wave whose lane ends gate-red in /build having pushed nothing
A Wave completion only
  • 3-wave fleet — the orchestrator ends 3 times; each tick holds one wave's dispatches, notifications and reconciliation
  • lane ends gate-red mid-pipeline — the wave is still complete (every lane reported), so the tick ends; that unit's commits live only in its worktree, which survives because teardown needs terminal: true
  • run moves machines — breaks — unpushed lane commits are local-only

Rejected because the same boundary with the safety half dropped: it leaves a gate-red lane commits only in its worktree, so the run cannot move machines and a recycled worktree loses them

Evidence: commands/start-multi.md:52; commands/start-multi.md:97

B Wave completion, and push every started branch firstrecommended
  • 3-wave fleet — identical to A, plus one push per started lane at the boundary
  • lane ends gate-red mid-pipeline — its commits reach origin, so the next tick can resume from any tree
  • run moves machines — survives — this is the existing cost-stop protocol, generalised to every yield

Evidence: commands/start-multi.md:52

C Any time, with lanes as detached claude -p processes
  • 3-wave fleet — the orchestrator ends whenever it likes; lanes write verdicts on their branches via lane-step-record
  • lane ends gate-red mid-pipeline — the verdict is on the branch, readable by any later tick
  • run moves machines — survives, but needs process management the plugin has never done and drops the Agent tool's notification path

Rejected because premise unverified: whether a claude -p exit kills its background subagents is a known-unknown; take it only if B's per-wave context still measures too large

Evidence: agents/unit-lane.md:21-40

Recommendation. B: /start-multi already defines a cost stop at exactly this boundary and already says what it costs to stop there: 'git push every started lane's branch first and keep its worktree, because a lane that has not reached /verify-build has pushed nothing.' A is that stop with the safety half dropped.

If overturned. C makes the driver a process supervisor and the tracer bullet becomes the subagent-lifetime probe instead of a two-unit fleet

Who re-dispatches the orchestrator, and what stops a driver looping forever

Something must re-invoke /start-multi after each yield. /build's yield already has this exact loop one level down, and it ships with a non-progress guard: 'k did not advance between two consecutive dispatches -> stop and report blocked-on=build-no-progress; a yield that resumes onto the same slice forever is the one way this loop costs more than it saves.' Whatever drives the orchestrator needs the same guard.

  • a 3-wave fleet run overnight
  • a wave that yields without advancing because its lane keeps dying
A A shell driver (bin/fleet-loop)recommended
  • 3-wave fleet overnight — one fresh claude -p per tick until the verdict is terminal; no context survives between ticks
  • wave does not advance — the driver owns the guard: compare waves=k/N across two ticks and stop on no progress, mirroring build-no-progress
  • census — a bin/ script with a scripts/ implementation and a test-*.sh; the agent census stays 11, and the bin/ name is a contract from the day it ships

Evidence: agents/unit-lane.md:64-72; commands/build.md:90

B The human re-invokes each tick
  • 3-wave fleet overnight — does not run overnight; unattended is /start-multi's stated contract
  • wave does not advance — the human sees it, so no mechanical guard is needed
  • census — nothing new ships

Rejected because breaks the unattended contract the command states in its first line

C /loop inside one session
  • 3-wave fleet overnight — runs, but the babysitter's own context is the 403k-median row; it re-loads the orchestration bodies into a context that never ends
  • wave does not advance — the babysitter would have to hold the guard in prose, in the context we are trying to end
  • census — nothing new ships

Rejected because it re-creates the unbounded context this work exists to remove

Recommendation. A: it is the only option that keeps the unattended contract while ending the context, and the guard it must carry is already specified and proven one level down in unit-lane's /build loop

If overturned. B drops the driver slice entirely and the work is only the yield plus the resume point

GH-429-F3 · GH-429 · decided (owner): B

How a yield is spelled in the verdict line

The issue proposed a new marker carrying outcome=yield. The evidence says that word has nowhere to land. remote-ai-agents' verdict.ts hardcodes exactly three outcomes (success, gate-red, blocked-on) and maps anything else to infra with infraReason 'unknown-outcome'; unit-lane's spec block emits the same three. /build already expresses a yield without a fourth word: 'a yield is a success whose slices= is short of its total.' Separately, lane-step-parse.py enforces no enum at all but does hardcode the marker token LANE-STEP:v(\d+).

  • the driver reads the tick's verdict to decide whether to tick again
  • remote-ai-agents leases a step and reads the same line
A New marker FLEET-STEP:v1, with outcome=yield
  • driver reads the tick — works — the driver is new code and can know the word
  • remote-ai-agents reads it — unknown-outcome -> infra, if the line ever reaches that reader
  • a reader of both markers — two yield vocabularies in one flow: success-with-short-counts at the slice level, outcome=yield at the wave level

Rejected because invents a fourth outcome word for a concept the flow already spells a different way one level down

B New marker FLEET-STEP:v1, reusing the three outcomes; a yield is success with waves=k/N short of totalrecommended
  • driver reads the tick — success with k<N means tick again, exactly as unit-lane reads slices=3/8
  • remote-ai-agents reads it — the outcome vocabulary is the one it already knows; only the marker token differs
  • a reader of both markers — one yield idiom at both levels; lane-step-parse needs its marker parameterised and nothing else, since its attribute grammar already accepts waves=k/N

Evidence: agents/unit-lane.md:64-72; scripts/lane-step-parse.py:64; remote-ai-agents/src/scheduler/verdict.ts:109-113

C Reuse LANE-STEP:v1 with step=start-multi
  • driver reads the tick — works with today's parser unchanged
  • remote-ai-agents reads it — verdict.ts compares step against the step the scheduler leased, so an unleased step is wrong-step -> infra; it holds no enum, so this is about the lease, not a list
  • a reader of both markers — one marker for two different things: a pipeline step and a fleet tick

Rejected because conflates a step's verdict with a run's; the orchestrator is not one of the five leased steps

Recommendation. B: it is the only option that adds a marker without adding a vocabulary. The correction that drives it: the blocker on C is verdict.ts's expectedStep lease, not a step= enum, and the blocker on A is the three-value OUTCOMES table, which the issue attributed to the wrong place.

If overturned. A costs a fourth outcome in every reader that ever sees the line; C costs no code today and a conflated contract later

GH-429-F4 · GH-429 · decided (owner): B

Is the resume point stored, or derived from the units

The issue proposes three additive run.yaml keys: waveBudget, wavesDone and phase. But /start-multi already carries units[].wave plus step and status, and /design-multi already carries units[].step as pending|drafting|critiqued|resolved|written|done, which is the phase. And the command itself states the principle: 'Git is the primary signal and the state file a hint', naming 'a state file that says step: plan while the branch carries three slices' as the orchestrator's commonest misread. A stored resume pointer is exactly that kind of second truth.

  • a tick is killed between dispatch and collection
  • a lane advances after the orchestrator wrote run.yaml
A Store all three: waveBudget, wavesDone, phase
  • tick killed mid-wave — wavesDone says the wave finished; the units say otherwise; the stored value wins and a wave is skipped
  • lane advances after the write — the pointer is stale in the dangerous direction
  • reading the run — one line to read

Rejected because denormalises state the units already determine, in a file the command already calls a hint

B Store only waveBudget; derive wave progress and phase from units[]recommended
  • tick killed mid-wave — the next tick derives progress from units[] and git, and re-enters the incomplete wave, which is step 4's existing resume rule
  • lane advances after the write — nothing to go stale; the derivation reads the current units
  • reading the run — one derivation, which is the same one step 4 already performs

Evidence: commands/start-multi.md:73; commands/start-multi.md:81; commands/start-multi.md:114; commands/design-multi.md:126

C Store all three, but treat them as hints re-derived on read
  • tick killed mid-wave — safe, because the derivation runs anyway
  • lane advances after the write — safe, same reason
  • reading the run — the stored value is now decoration that must be kept honest by every writer, for no read that trusts it

Rejected because pays the write cost of a cache nothing is allowed to read

Recommendation. B: waveBudget is a policy input and genuinely not derivable, so it is stored; wavesDone and phase are projections of units[], and the repo has already named the failure mode of storing them.

If overturned. A makes the invariant 'run.yaml changes are additive' true in letter and adds the misread the command warns about
