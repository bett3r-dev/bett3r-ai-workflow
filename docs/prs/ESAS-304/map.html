What the end-of-design scaffold commit contains when a design adds events or commands

What does the end-of-design scaffold commit contain when a design adds events or commands? The scaffolder writes whole new files only. A new read model or policy that names a proposed event refers to a symbol that exists only as a fragment, so the commit does not typecheck (probe G: TS2339). ESAS-304's ticket says /build places fragments. ESAS-289 and ESAS-292 found that this leaves the owner's 'one commit with everything agreed' thin, or red.

  • A design adds event 'Ui Widget Layout Archived' on an existing aggregate plus a read model projecting it (teselly analytics)
  • A design adds only a read model over existing events
  • A design adds a brand-new kixie aggregate (needs one barrel line in @kixie/schemas)
A Mechanical only: create-only scaffolder + guarded EOF barrel append; any file that names a fragment-only symbol is deferred to STILL OWED for /build
  • New event + read model — Read model deferred; commit is thin but green
  • Read model over existing events — Identical across options
B Mechanical + placement: as A, then an agent in /design places topology fragments (new commands, events, their schemas; never registration), re-runs the scaffolder, and commits only if the repo's typecheck passesrecommended
  • New event + read model — Everything agreed lands in one green commit
  • Agent places a fragment wrongly — Caught before commit
C Leave it red: commit everything; the scaffold commit may fail typecheck and /build fixes it
  • New event + read model — Red commit

Rejected because Breaks the owner's stated bar 'the scaffold commit must build'.

Recommendation. B: Only B delivers 'one commit with all the scaffolding agreed' when a design adds events, which most designs do. The typecheck gate makes the agent's edit safe. A is the floor B builds on (the scaffolder stays create-only plus the barrel append, ESAS-292 and ESAS-300), so B costs one extra agent step in ESAS-304.

If overturned. A: ESAS-304 keeps 'fragments never written in /design', and the report is honest that the commit is partial. C is ruled out by the owner's bar.

ESAS-304 · What counts as 'agreed' on the eventstorming board for the design-end scaffold

design.json has no accept state (DesignFile = propose/modify/remove/comments, BP design.ts:142-154; DesignStatus proposed|modified|removed|satisfied, nodes.ts:14). The scaffolder plans every coherent design.propose entry not yet extracted (filterDesign plan.ts:74). 'Everything agreed on both boards' therefore has no ES-side meaning today.

  • An AI proposal nobody discussed
  • A proposal with an unresolved comment questioning it
  • A human proposal
  • A proposal withdrawn by remove
A Everything proposed and coherent is agreed (today's planner semantics)
  • Open question on a proposal — Diverges: scaffolds what is still being questioned.
B Explicit accept step on the ES layer (new design-layer state + op in BP, unowned in this run)
  • Open question on a proposal — Needs a blueprint-schema bump, both stores and board UI; no ticket owns it.
C Proposed and coherent, minus any element with an unresolved comment anchored on itrecommended
  • Open question on a proposal — Uses state the layer already has (DesignComment.resolved, commentAnchorKey).

Recommendation. C: Expresses 'not agreed yet' with state the layer already has and no new BP work; held elements are visible in the report; B is the long-term answer to file if an explicit Accept gesture is wanted.

If overturned. A: the report has no 'held' section and open questions get scaffolded. B: file a blueprint ticket for an accept op and hold the scaffold step on it.
