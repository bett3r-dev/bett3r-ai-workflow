BP-196-F1 · BP-196 · skill-path resolver + /build relays framework skill file and plugin root to executor and verifier · decided (owner): refuse-before-start

When the framework skill a repo declares cannot be found on this machine, what should /build do?

Every repo we build in declares a framework skill in .blueprint.config.json (blueprint and teselly: bett3r-pv3-ai-skills:scaffold-from-design; kixie: ddd:scaffold-from-design). After this ticket /build looks that name up among the installed plugins and hands the file to the coding and reviewing agents. The lookup can fail: the plugin is not installed (on this laptop ddd is missing, so a kixie build here would hit it), the plugin runs from a source checkout, or the name is misspelled. Today nothing notices: /build prints one line (build.md:49), and in a fleet that line always prints, and the agent writes framework code without the framework's rules.

  • A kixie fleet started from a machine without the ddd plugin
  • A developer running the plugin from a source checkout
  • A typo in designTooling.scaffoldSkill
  • A repo that declares no framework skill
carry-on Carry on: each slice runs and records the missing skill as a deviation the reviewer weighs
  • kixie fleet without ddd — The code is written and committed without the framework rules; you learn it from the PR record.
block-slice Stop each slice that touches framework code with BLOCKED
  • kixie fleet without ddd — Each lane spends its provisioning and stops at its first framework slice with the same message.
refuse-before-start Check once before anything runs: /build Step 1 and /start-multi before provisioning refuse with the missing plugin and install commandrecommended
  • kixie fleet without ddd — The run refuses in seconds instead of building blind or stopping lane by lane.
  • no framework skill declared — A repo that declares nothing is unaffected.

Recommendation. refuse-before-start: The failure is a fact about the machine, not about any slice, so it should be found once and before any compute is spent. Writing framework code blind is the quality loss this ticket exists to remove.

If overturned. carry-on: rule 3 records the deviation and the verifier adjudicates it; block-slice: the executor reports BLOCKED on a framework slice; in both, start-multi.md is untouched.

BP-196-F2 · BP-196 · PV3 create-* skills open with a 'Starting from a scaffold' section · decided (owner): include

Should this ticket also give the PV3 create-* skills a 'Starting from a scaffold' section, as the kixie ones have?

Once the coding agent reads the framework skills, it reads them as written. kixie's ddd create-aggregate, create-policy, create-readmodel, create-schema and create-flow-tests each open with a 'Starting from a scaffold' section: keep the file's names, ids and placement, and work only the TODO(scaffold) markers. The PV3 skills in this same plugin repo have none; they walk through building the artifact from nothing. The PV3 bridge says to keep the identity once (scaffold-from-design Step 4); the create-* file the agent then opens does not repeat it.

  • A PV3 slice whose aggregate the scaffold already wrote
  • A PV3 slice with no scaffold (hand-written)
  • A kixie slice
include Add a short 'Starting from a scaffold' section to the five PV3 create-* skills (aggregate, policy, read model, schema, tests), matching kixie'srecommended
  • scaffolded PV3 aggregate — The agent is told up front not to rename or move what the design fixed.
defer Ship the path relay alone and file the PV3 sections as a follow-up
  • scaffolded PV3 aggregate — PV3 agents get the skills but follow them from the top.

Recommendation. include: The skills are in the same repo and the edit is small. Without it, the PV3 half of this ticket hands the agent a guide written for a situation it is not in.

If overturned. File a follow-up for the five PV3 create-* sections; the relay ships unchanged.
